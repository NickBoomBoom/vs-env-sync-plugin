# 按 Git 分支隔离 Env 数据设计

## 目标

同一 Git 项目的不同分支分别保存 env 文件，切换分支后只同步当前分支的数据；已有共享数据在首次访问分支时继承，避免升级后丢失已有配置。

## 范围与约束

- 沿用现有配置仓库及其 `envSync.configRepoBranch`，不为每个项目切换配置仓库的 Git 分支。
- 旧共享数据只读继承、不删除；旧版本插件仍能读取旧数据，但无法读取新版本的分支数据。
- 仅同步现有路径正则命中的文件，不改变冲突提示、防抖和串行队列行为。
- detached HEAD 没有分支名称，跳过该项目并记录警告，避免多个无分支状态互相覆盖。

## 方案比较

1. **项目目录下增加 `branches/`（已选择）**：分支数据为 `projects/<host>/<owner>/<repo>/branches/<编码分支名>/`。项目数据集中，但需要让旧目录读取排除 `branches/`。
2. **独立顶层 `project-branches/`**：新旧数据完全分开，读取逻辑较简单，但配置仓库会出现两套项目层级。
3. **使用配置仓库的 Git 分支**：会改变现有配置分支语义，并增加切换、拉取和推送复杂度，不采用。

## 存储与分支识别

- 通过 `git symbolic-ref --quiet --short HEAD` 获取项目当前分支。
- 分支名使用 `encodeURIComponent` 编码为单个目录段，例如 `feature/login` 映射为 `feature%2Flogin`。
- 新分支数据写入项目下的 `branches/<编码分支名>/`。
- 现有 Git 文件监听器继续负责在 HEAD 或 refs 变化时使上下文缓存失效；重新解析后使用新分支目录。

## 旧数据继承

- 当前分支目录不存在，且旧项目目录中存在匹配的 env 文件时，把这些文件复制到当前分支目录，并提交、推送这次继承。
- 继承完成后执行现有打开工作区同步或本地变更推送逻辑；本地与继承内容冲突时仍由用户选择。
- 当前分支目录一旦存在，就只读写该目录，不再回退到旧共享数据。
- 旧项目目录保持不变；读取旧数据时排除 `branches/`，防止自定义正则误把分支文件当成共享文件。
- 没有旧数据或没有当前分支目录时，维持现有空远端行为。

## 验证

- 不同分支读写各自目录，分支名包含 `/` 时路径仍安全。
- 首次访问可复制旧共享数据，后续修改不影响旧数据和其他分支。
- 已有分支目录时不重复继承；旧目录扫描不会包含 `branches/`。
- detached HEAD 不执行同步。
